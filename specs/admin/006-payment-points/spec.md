**建立日期**：2026-03-27
**狀態**：草稿
**介面類型**：後台管理介面（Admin Panel）
**存取角色**：ROLE_ADMIN

## 頁面與介面清單

### 頁面 1 — 儲值方案管理頁
- **路由**：`/admin/payment/plans`
- **存取權限**：ROLE_ADMIN
- **UI 元件**：
  - 頁面標題「儲值方案管理」
  - 「新增方案」按鈕（右上角）
  - 資料表格：
    - 欄位：方案名稱（金幣數量）、贈送金幣、定價（NT$）、狀態（啟用／停用）、操作（編輯、停用／啟用、刪除）
    - 狀態徽章：啟用（綠）、停用（灰）
  - 空狀態提示

### 頁面 2 — 新增／編輯儲值方案 Modal
- **路由**：`/admin/payment/plans`（Modal 覆蓋）
- **存取權限**：ROLE_ADMIN
- **UI 元件**：
  - Modal 標題「新增儲值方案」／「編輯儲值方案」
  - 金幣數量輸入（正整數，必填）
  - 贈送金幣數量輸入（正整數，0 代表無贈送，必填）
  - 定價輸入（NT$，正整數，必填）
  - 啟用狀態切換（Toggle，預設啟用）
  - 方案預覽卡片（即時顯示效果）
  - 儲存／取消按鈕

### 頁面 3 — 玩家點數查詢與手動調整頁
- **路由**：`/admin/payment/wallet`
- **存取權限**：ROLE_ADMIN
- **UI 元件**：
  - 頁面標題「玩家點數管理」
  - 玩家搜尋區（Email 或 ID 搜尋，點擊「查詢」）
  - 玩家點數資訊卡片（顯示金幣餘額、贈點餘額）
  - 「手動調整點數」按鈕
  - 調整記錄表格（該玩家的交易歷程）

### 頁面 4 — 手動調整點數 Modal
- **路由**：`/admin/payment/wallet`（Modal 覆蓋）
- **存取權限**：ROLE_ADMIN
- **UI 元件**：
  - Modal 標題「手動調整點數」
  - 目標玩家顯示（唯讀，email + 暱稱）
  - 金幣調整數量（可正可負，帶符號輸入，如 +100 或 -50）
  - 贈點調整數量（可正可負）
  - 調整原因（必填文字輸入，最多 200 字）
  - 確認 / 取消按鈕
  - 警告文字：「此操作將直接修改玩家帳戶餘額，請謹慎操作。」

### 頁面 5 — 全站交易記錄頁
- **路由**：`/admin/payment/transactions`
- **存取權限**：ROLE_ADMIN
- **UI 元件**：
  - 頁面標題「交易記錄」
  - 篩選列：玩家 Email／ID 搜尋、交易類型下拉（全部、儲值、消費、退款、手動調整）、日期範圍
  - 資料表格：
    - 欄位：時間、玩家 Email、交易類型、金幣變動（+ / -）、贈點變動、備註／原因
  - 匯出 CSV 按鈕（若後端支援）

## 使用者情境與測試

### 使用者故事 1 — 管理員新增儲值方案（優先級：P1）

管理員建立新的儲值方案（如充值 300 金幣送 30 贈點，售價 NT$300）並立即啟用，讓玩家可選擇儲值。

**此優先級的原因**：儲值方案是平台收益基礎，新增功能是最基本操作。

**獨立測試**：使用 Admin 帳號進入方案管理，新增一筆方案，確認出現在列表並標記啟用。

**驗收情境**：
1. **在** 方案列表頁，**當** 管理員填寫金幣 300、贈點 30、定價 300 並點擊儲存，**則** 新方案出現在列表，狀態為「啟用」。
2. **在** 金幣數量欄位輸入非正整數或負數，**當** 點擊儲存，**則** 顯示驗證錯誤「金幣數量必須為正整數」。
3. **在** 方案已啟用，**當** 管理員點擊「停用」，**則** 狀態徽章變為「停用（灰色）」，玩家前台不再顯示此方案。

---

### 使用者故事 2 — 管理員手動調整玩家點數（優先級：P1）

因客服需求或補償，管理員需要手動增加或扣除特定玩家的金幣或贈點，並記錄原因。

**此優先級的原因**：點數調整是後台客服操作的核心功能，需要完整審計軌跡。

**獨立測試**：使用存在的玩家 Email，查詢並執行 +100 金幣調整，確認調整後餘額正確顯示。

**驗收情境**：
1. **在** 搜尋特定玩家後，**當** 管理員填寫金幣 +100、原因「新年活動補償」並確認，**則** 玩家金幣餘額增加 100，調整記錄出現在交易歷程。
2. **在** 調整後玩家金幣餘額將為負數（如餘額 50，調整 -100），**當** 管理員確認送出，**則** 系統是否允許需與後端確認；若不允許需顯示「調整後餘額不得為負」提示。
3. **在** 調整原因為空，**當** 點擊確認，**則** 顯示驗證錯誤「請填寫調整原因」。

---

### 使用者故事 3 — 管理員查詢交易記錄（優先級：P2）

管理員審查特定玩家的所有點數異動記錄，或過濾特定類型的交易進行稽核。

**此優先級的原因**：交易記錄查詢屬於管理監控功能，輔助客服處理糾紛。

**驗收情境**：
1. **在** 交易記錄頁，**當** 輸入玩家 Email 並搜尋，**則** 列表篩選顯示該玩家所有交易記錄。
2. **在** 交易記錄頁，**當** 選擇交易類型「手動調整」，**則** 僅顯示管理員手動調整的記錄，包含操作員資訊（若後端提供）。
3. **在** 設定日期範圍，**當** 查詢，**則** 僅顯示該時間區間的交易記錄。

---

### 邊界情況

- 搜尋不存在的玩家 Email，顯示「找不到符合條件的玩家」。
- 儲值方案定價為 0 或負數，驗證拒絕。
- 手動調整金額為 0，驗證提示「調整金額不得為 0」。
- 交易記錄無資料時，顯示空狀態。
- 管理員角色以外的角色嘗試訪問此頁面，導向 403 頁面。

## API 串接規格

### 儲值方案管理

| 動作 | Method | 端點 | 主要 Request 欄位 | 主要 Response 欄位 | 前端 UI 狀態 |
|------|--------|------|------------------|--------------------|-------------|
| 取得方案列表 | GET | `/api/admin/recharge/plans` | — | `[{id, goldAmount, bonusAmount, price, isActive}]` | loading → 表格渲染 |
| 新增方案 | POST | `/api/admin/recharge/plans` | `goldAmount, bonusAmount, price, isActive` | `{id, goldAmount, bonusAmount, price, isActive}` | 按鈕 loading → Toast → Modal 關閉 |
| 更新方案 | PUT | `/api/admin/recharge/plans/{id}` | `goldAmount, bonusAmount, price, isActive` | `{id, ...}` | 按鈕 loading → Toast |
| 刪除方案 | DELETE | `/api/admin/recharge/plans/{id}` | — | `{success: true}` | 確認 Dialog → loading → 列表移除 |

### 玩家點數管理

| 動作 | Method | 端點 | 主要 Request 欄位 | 主要 Response 欄位 | 前端 UI 狀態 |
|------|--------|------|------------------|--------------------|-------------|
| 手動調整點數 | POST | `/api/admin/wallet/adjust` | `userId, goldAmount, bonusAmount, reason` | `{userId, goldCoins, bonusCoins}` | Modal loading → Toast → 餘額更新 |
| 查詢交易記錄 | POST | `/api/admin/wallet/transactions` | `condition:{userId, type, startDate, endDate}` | `[{id, userId, email, type, goldChange, bonusChange, reason, createdAt}]` | loading → 表格渲染 |
| 查詢玩家列表 | GET | `/api/admin/users` | — | `[{id, email, nickname}]` | 搜尋 loading |

## 功能需求（前端 UI）

### 介面需求

- **FR-UI-001**：方案列表以卡片式或表格式呈現，每筆方案顯示「儲值 X 金幣，贈送 Y 贈點，NT$ Z」的視覺化格式。
- **FR-UI-002**：新增方案 Modal 右側顯示「方案預覽」，即時反映輸入值的呈現效果。
- **FR-UI-003**：手動調整點數的金額輸入框：支援正負值輸入，並以顏色區分（正數綠色、負數紅色）。
- **FR-UI-004**：玩家點數資訊卡片顯示：金幣餘額（黃色 icon）、贈點餘額（藍色 icon），調整後即時更新。
- **FR-UI-005**：交易記錄的金幣／贈點變動欄位以顏色區分：正值（+）顯示綠色，負值（-）顯示紅色。
- **FR-UI-006**：交易類型以中文標籤顯示：儲值、抽獎消費、退款、手動調整（管理員）、兌換。
- **FR-UI-007**：停用中的儲值方案以半透明或灰階樣式顯示，操作按鈕變更為「啟用」。
- **FR-UI-008**：刪除方案前顯示二次確認：「確定刪除此儲值方案？若有玩家正在使用此方案，請先停用。」

### 狀態管理

- **SM-001**：頁面初始載入顯示 skeleton loading。
- **SM-002**：API 錯誤時顯示 Toast，說明失敗原因。
- **SM-003**：點數調整成功後，顯示 Toast「點數已成功調整」，並更新玩家餘額卡片顯示。
- **SM-004**：方案啟用／停用切換以樂觀更新（optimistic update）即時反映，若 API 失敗則回滾狀態。
- **SM-005**：玩家搜尋使用 debounce 300ms，避免頻繁 API 請求。

## API 驗證清單

- **AV-001** ✅：`POST /api/admin/wallet/adjust` 支援 `goldAmount` 和 `bonusAmount` 分別調整 — 符合前端分別顯示金幣與贈點的需求。
- **AV-002** ✅：`POST /api/admin/wallet/transactions` 支援 `userId`、`type`、`startDate`、`endDate` 篩選 — 符合交易記錄篩選需求。
- **AV-003** ⚠️：`DELETE /api/admin/recharge/plans/{id}` — 後端未說明若方案正被使用中是否允許刪除；前端需根據後端回應顯示適當錯誤（如「此方案有進行中的儲值交易，無法刪除」）。
- **AV-004** ❌：玩家點數查詢 API — `GET /api/admin/users` 提供玩家列表但未包含個別玩家的點數餘額；需確認是否有 `GET /api/admin/users/{id}` 或 `GET /api/admin/wallet/{userId}` 端點提供餘額資訊。
- **AV-005** ⚠️：`POST /api/admin/wallet/adjust` 負數調整驗證 — 後端是否驗證調整後餘額不得為負數未明確說明；前端應加入預檢提示，但最終依賴後端業務邏輯。
- **AV-006** ⚠️：交易記錄的 `type` 欄位值 — 後端未明確列出所有可能的 type 值（如 RECHARGE、DRAW、REFUND、MANUAL_ADJUST 等）；前端下拉選單需與後端確認完整 enum 清單。
- **AV-007** ❌：方案停用 API — 後端僅提供 `PUT /api/admin/recharge/plans/{id}` 含 `isActive` 欄位；無獨立的 enable/disable 端點，前端需以 `PUT` 並帶 `isActive: false` 實現停用。
- **AV-008** ⚠️：交易記錄的操作員資訊 — 手動調整記錄是否包含「操作員 email」未在 Response 說明中體現，需確認後端是否有 `operatorEmail` 或 `operatorId` 欄位用於稽核。

凡例：✅ 已確認一致 | ⚠️ 需要確認 | ❌ 發現缺口或不一致

## 成功標準

### 可量化的成果

- **SC-001**：管理員可在 4 步驟內完成手動點數調整（搜尋玩家 → 點擊調整 → 填寫原因 → 確認）。
- **SC-002**：儲值方案列表載入時間不超過 1 秒（方案數量預期不超過 20 筆）。
- **SC-003**：手動調整完成後，玩家餘額資訊即時更新（無需重新整理頁面）。
- **SC-004**：交易記錄列表支援組合篩選（玩家 + 類型 + 日期區間同時生效）。
- **SC-005**：所有手動調整操作均記錄至交易歷程，可查詢稽核（100% 可追蹤）。
- **SC-006**：僅 ROLE_ADMIN 可存取此功能模組，ROLE_STORE_OWNER 無法看到此選單項目。
