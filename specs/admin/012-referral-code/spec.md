## 頁面與介面清單

### 頁面 1 — 推薦碼列表頁
- **路由**：`/admin/referral-codes`
- **存取權限**：ROLE_ADMIN
- **UI 元件**：
  - 頁面標題「推薦碼管理」
  - 篩選列：
    - 店家下拉（全部 / 特定店家，資料來自 `/api/admin/stores/options`）
    - 狀態下拉（全部 / 啟用 / 停用）
    - 關鍵字搜尋（推薦碼文字）
  - 「新增推薦碼」按鈕（右上角）
  - 資料表格：
    - 欄位：推薦碼（帶複製按鈕）、關聯店家、狀態徽章、使用次數、建立時間、操作
    - 狀態徽章：啟用（綠）、停用（灰）
    - 操作：查看統計、啟用／停用、複製碼
  - 空狀態提示

### 頁面 2 — 新增推薦碼 Modal
- **路由**：`/admin/referral-codes`（Modal 覆蓋）
- **存取權限**：ROLE_ADMIN
- **UI 元件**：
  - Modal 標題「新增推薦碼」
  - 關聯店家選擇器（必選，下拉搜尋）
  - 推薦碼輸入（可選，留空則由系統自動生成）
    - 若填寫：說明「僅允許英文大寫字母與數字，6-12 字元」
    - 若留空：顯示「系統將自動生成推薦碼」提示
  - 預覽：若已輸入碼值，右側顯示格式驗證結果（✅ 格式正確 / ❌ 格式有誤）
  - 確認 / 取消按鈕

### 頁面 3 — 推薦碼統計詳情頁
- **路由**：`/admin/referral-codes/{id}/stats`
- **存取權限**：ROLE_ADMIN
- **UI 元件**：
  - 頁面標題「推薦碼統計 — {code}」
  - 返回列表按鈕
  - 概覽數據卡片（3 張）：
    - 推薦碼文字（帶複製按鈕）
    - 關聯店家名稱
    - 總推薦人數（totalReferred）
  - 推薦玩家列表表格：
    - 欄位：玩家 Email（部分遮罩）、玩家 ID、註冊時間
  - 列表依「註冊時間 DESC」排序
  - 時間軸／圖表（可選）：每月推薦人數趨勢

## 使用者情境與測試

### 使用者故事 1 — Admin 為店家新增推薦碼（自動生成）（優先級：P1）

Admin 為新開設的店家建立推薦碼，讓店家可以分享給潛在玩家使用，玩家註冊時輸入此碼即建立推薦關係。

**此優先級的原因**：推薦碼是玩家獲取的核心管道，新店家上線後即需要。

**獨立測試**：Admin 登入，選擇一間測試店家，不填寫碼值直接送出，確認系統生成的碼出現在列表。

**驗收情境**：
1. **在** 新增推薦碼 Modal，**當** 選擇店家「測試店家 A」、不填寫碼值並確認，**則** 系統生成推薦碼（如 ABC12345），出現在列表，狀態為「啟用」。
2. **在** 新增推薦碼 Modal，**當** 手動輸入碼值「KUJI2026」並確認，**則** 以指定碼值建立推薦碼。
3. **在** 未選擇關聯店家，**當** 點擊確認，**則** 顯示驗證錯誤「請選擇關聯店家」。

---

### 使用者故事 2 — Admin 停用特定推薦碼（優先級：P1）

店家停止合作或推薦碼被濫用時，Admin 需要立即停用，防止新玩家使用此碼註冊。

**此優先級的原因**：停用功能是推薦碼管理的安全控制機制。

**獨立測試**：選擇一個啟用中的推薦碼，點擊停用，確認狀態變更，再以玩家端嘗試使用此碼驗證後端拒絕。

**驗收情境**：
1. **在** 推薦碼狀態為「啟用」，**當** Admin 點擊「停用」，**則** 狀態徽章即時變為「停用（灰色）」，玩家端無法使用此碼。
2. **在** 推薦碼狀態為「停用」，**當** Admin 點擊「啟用」，**則** 狀態恢復為「啟用（綠色）」，玩家端可正常使用。
3. **在** 關聯店家被停用，**當** 查看推薦碼列表，**則** 相關推薦碼顯示「店家已停用」警告 icon。

---

### 使用者故事 3 — Admin 查看推薦碼使用統計（優先級：P2）

Admin 需要了解各推薦碼的推薦效果，分析哪間店家推薦活動最活躍。

**此優先級的原因**：統計功能支援運營決策，屬於輔助功能。

**驗收情境**：
1. **在** 推薦碼列表，**當** Admin 點擊某推薦碼的「查看統計」，**則** 導向統計詳情頁，顯示總推薦人數及推薦玩家列表。
2. **在** 統計詳情頁，**當** 查看玩家列表，**則** 玩家 Email 以部分遮罩顯示（如 `abc***@gmail.com`），保護隱私。
3. **在** 推薦碼無任何推薦記錄，**當** 進入統計頁，**則** 顯示「總推薦人數：0」，玩家列表顯示空狀態「此推薦碼尚未被使用」。

---

### 使用者故事 4 — Admin 複製推薦碼分享（優先級：P3）

Admin 需要快速複製推薦碼分享給店家，方便其向玩家推廣。

**驗收情境**：
1. **在** 推薦碼列表，**當** Admin 點擊推薦碼旁的「複製」icon，**則** 推薦碼文字複製到剪貼板，顯示 Toast「已複製到剪貼板」。

---

### 邊界情況

- 手動輸入的推薦碼已被使用，後端返回錯誤，前端顯示「此推薦碼已存在，請嘗試其他碼值」。
- 推薦碼格式不符合規則（含特殊字元、過短/過長），即時顯示格式驗證錯誤。
- 一間店家可有多個推薦碼（FR-012 說明一店多碼），列表可依店家篩選查看所有關聯碼。
- 刪除推薦碼（若提供此功能）需二次確認，且說明「已使用過此碼的推薦關係不受影響（不可更改）」。

## API 串接規格

### 推薦碼管理

| 動作 | Method | 端點 | 主要 Request 欄位 | 主要 Response 欄位 | 前端 UI 狀態 |
|------|--------|------|------------------|--------------------|-------------|
| 取得推薦碼列表 | GET | `/api/admin/referral-codes` | — | `[{id, code, storeId, storeName, enabled, usageCount, createdAt}]` | loading → 表格渲染 |
| 新增推薦碼 | POST | `/api/admin/referral-codes` | `storeId, code(可選)` | `{id, code, storeId, storeName, enabled, createdAt}` | Modal loading → Toast → 列表更新 |
| 啟用推薦碼 | PUT | `/api/admin/referral-codes/{id}/enable` | — | `{id, enabled: true}` | 按鈕 loading → 狀態徽章更新 |
| 停用推薦碼 | PUT | `/api/admin/referral-codes/{id}/disable` | — | `{id, enabled: false}` | 按鈕 loading → 狀態徽章更新 |
| 取得推薦統計 | GET | `/api/admin/referral-codes/{id}/stats` | — | `{code, storeId, storeName, totalReferred, referrals:[{userId, email, registeredAt}]}` | loading → 統計渲染 |
| 取得店家選單 | GET | `/api/admin/stores/options` | — | `[{id, name}]` | 下拉選單載入 |

## 功能需求（前端 UI）

### 介面需求

- **FR-UI-001**：推薦碼列表的「推薦碼」欄位旁顯示複製 icon，點擊複製至剪貼板。
- **FR-UI-002**：新增 Modal 中推薦碼輸入欄位：即時格式驗證（輸入時），規則為大寫英數字 6-12 碼。
- **FR-UI-003**：推薦碼輸入留空時，輸入框顯示佔位文字「留空則系統自動生成」。
- **FR-UI-004**：統計詳情頁的玩家 Email 遮罩顯示（`ab****@domain.com`），保護個資。
- **FR-UI-005**：推薦碼啟用／停用以 Toggle 開關或動態按鈕（啟用中→點擊停用）呈現。
- **FR-UI-006**：推薦碼的店家關聯標示：若關聯店家已停用，顯示警告 icon 與 tooltip「關聯店家已停用，此碼無法使用」。
- **FR-UI-007**：「使用次數」欄位顯示 `usageCount`，點擊可直接跳轉至統計頁面。
- **FR-UI-008**：篩選列：店家下拉（從 `/api/admin/stores/options` 取得）、狀態下拉（全部/啟用/停用）、推薦碼關鍵字。

### 狀態管理

- **SM-001**：列表初始載入使用 skeleton loading。
- **SM-002**：啟用／停用使用樂觀更新（optimistic update），若 API 失敗則回滾並顯示 Toast 錯誤。
- **SM-003**：新增成功後，Toast「推薦碼已建立」，列表重新載入。
- **SM-004**：複製到剪貼板後，顯示 Toast「已複製到剪貼板」，2 秒後自動消失。
- **SM-005**：篩選條件變更自動觸發查詢（關鍵字 debounce 300ms）。

## API 驗證清單

- **AV-001** ✅：`POST /api/admin/referral-codes` 的 `code` 欄位為可選 — 支援自動生成與手動輸入兩種模式。
- **AV-002** ✅：`PUT /api/admin/referral-codes/{id}/enable` 和 `/disable` 為獨立端點 — 啟停操作清晰。
- **AV-003** ✅：`GET /api/admin/referral-codes/{id}/stats` 包含 `referrals` 陣列 — 統計詳情頁有資料來源。
- **AV-004** ⚠️：`GET /api/admin/referral-codes` 無篩選參數 — 後端 spec 未說明此 GET 是否支援 query param 篩選（如 `?storeId=&enabled=`）；若不支援，前端需在客戶端進行篩選，可能影響效能（資料量大時）。
- **AV-005** ❌：刪除推薦碼 API — 後端 spec 未提供 `DELETE /api/admin/referral-codes/{id}` 端點；若後台需要刪除功能，需與後端確認是否支援或設計軟刪除機制。
- **AV-006** ⚠️：推薦碼格式規則 — 後端 spec 未明確說明推薦碼的格式規範（長度、字元集）；前端 UI 暫定「大寫英數字 6-12 碼」，需與後端確認實際驗證規則。
- **AV-007** ⚠️：`referrals[].email` 完整性 — `GET /api/admin/referral-codes/{id}/stats` 回傳 `referrals[].email` 欄位；需確認此為完整 email 還是已遮罩版本（後端遮罩 vs 前端遮罩）。
- **AV-008** ❌：一店多碼顯示 — `GET /api/admin/referral-codes` Response 無明確的「一店多碼」標示或分組；前端若需按店家分組顯示推薦碼，需透過篩選或前端分組實現。

凡例：✅ 已確認一致 | ⚠️ 需要確認 | ❌ 發現缺口或不一致

## 成功標準

### 可量化的成果

- **SC-001**：Admin 可在 2 步驟內（選擇店家 → 確認）完成一個推薦碼的自動生成建立。
- **SC-002**：推薦碼列表在 200 筆資料以內，載入時間不超過 2 秒。
- **SC-003**：推薦碼複製功能在所有主流瀏覽器（Chrome、Safari、Firefox）正常運作。
- **SC-004**：停用推薦碼後，前台玩家 100% 無法使用此碼完成註冊（後端保證）。
- **SC-005**：統計詳情頁顯示的玩家列表依「註冊時間 DESC」排序，便於查看最新推薦記錄。
- **SC-006**：僅 ROLE_ADMIN 可存取推薦碼管理頁面（RBAC 保護）。
