# 前端規格書（後台）：店家管理

**功能分支**：`014-store-management`
**對應後端 Spec**：`specs/014-store-management/spec.md`
**建立日期**：2026-03-27
**狀態**：草稿
**介面類型**：後台管理介面（Admin Panel）
**存取角色**：ROLE_ADMIN、ROLE_STORE_OWNER

---

## 頁面與介面清單

### 頁面 1 — 店家列表頁
- **路由**：`/admin/stores`
- **存取權限**：ROLE_ADMIN
- **UI 元件**：
  - 頁面標題「店家管理」
  - 篩選列：
    - 狀態下拉（全部 / 啟用 / 停用）
    - 關鍵字搜尋（店家名稱）
    - 排序下拉（建立時間 DESC/ASC）
  - 資料表格：
    - 欄位：Logo（縮圖）、店家名稱、簡短描述、店家管理員 Email、商品數量、狀態徽章、建立時間、操作
    - 狀態徽章：啟用（綠）、停用（灰）
    - 操作：查看詳情、編輯、啟用 / 停用
  - 空狀態提示「尚無店家資料，請至「帳號管理」建立第一位店家管理員以自動建立店家。」

### 頁面 2 — 店家詳情頁（Admin 查看）
- **路由**：`/admin/stores/{id}`
- **存取權限**：ROLE_ADMIN
- **UI 元件**：
  - 返回列表按鈕 + 麵包屑
  - 封面圖片橫幅（大圖展示）
  - 店家基本資訊卡片：
    - Logo（圓形裁切）、店家名稱、狀態徽章
    - 簡短描述
    - 完整描述（富文本渲染）
    - 聯絡資訊：Email、電話、地址
    - 社群連結：Facebook、Instagram（可點擊）
  - 店家管理員資訊（只有 Admin 可見）：Email、顯示名稱、狀態，點擊跳轉帳號詳情
  - 操作按鈕：「編輯店家資訊」、「啟用 / 停用」、「查看帳號」
  - 關聯商品概覽（顯示商品數量，連結到商品管理）

### 頁面 3 — 編輯店家資訊頁
- **路由**：`/admin/stores/{id}/edit`（Admin 編輯）或 `/admin/store/profile`（StoreOwner 編輯自家）
- **存取權限**：ROLE_ADMIN（任意店家）、ROLE_STORE_OWNER（僅自家店家）
- **UI 元件**：
  - 頁面標題「編輯店家資訊」
  - 返回按鈕
  - 基本資訊區塊：
    - 店家名稱（ROLE_ADMIN 可編輯；ROLE_STORE_OWNER 可編輯）
    - 簡短描述（必填，最多 100 字，字數計數）
    - 完整描述（富文本編輯器，可選）
  - 媒體上傳區塊：
    - Logo 圖片上傳（建議尺寸說明）
    - 封面圖片上傳
  - 聯絡資訊：
    - 店家 Email（格式驗證）
    - 店家電話
    - 店家地址
  - 社群連結（URL 格式驗證）：
    - Facebook 頁面連結
    - Instagram 主頁連結
  - 「儲存變更」/ 「取消」按鈕

### 頁面 4 — 停用店家確認 Modal
- **路由**：`/admin/stores/{id}`（Modal 覆蓋）
- **存取權限**：ROLE_ADMIN
- **UI 元件**：
  - Modal 標題「停用店家」
  - 嚴重警告區塊（紅色邊框）：
    - 「停用後，以下影響將立即生效：」
    - 清單：所有上架商品將自動下架、所有橫幅廣告將停用、店家對玩家不可見、關聯帳號無法登入（需確認：是否含帳號停用？）
    - 「已成立的訂單不受影響，仍可繼續處理。」
    - 「重新啟用不會自動恢復商品與廣告，需手動重新上架。」
  - 店家名稱輸入確認（輸入店家名稱才能啟用確認按鈕，防止誤操作）
  - 確認停用 / 取消按鈕

### 頁面 5 — StoreOwner 店家個人資料頁
- **路由**：`/admin/store/profile`
- **存取權限**：ROLE_STORE_OWNER
- **UI 元件**：
  - 頁面標題「店家資訊管理」
  - 說明：「STORE_EDITOR 無法編輯店家資訊（唯讀）」
  - 同編輯店家資訊頁的所有欄位（預填自家店家資料）
  - 若當前角色為 STORE_EDITOR，所有欄位為唯讀，顯示「您的角色無權編輯店家資訊」橫幅

## 使用者情境與測試

### 使用者故事 1 — Admin 查看與管理所有店家（優先級：P1）

Admin 在店家列表頁查看所有店家狀態，並快速識別需要處理的店家。

**此優先級的原因**：店家管理是平台運營的核心管理功能。

**獨立測試**：Admin 登入，確認列表顯示所有店家，含狀態、管理員 Email、商品數量。

**驗收情境**：
1. **在** Admin 進入店家列表，**當** 頁面載入，**則** 顯示所有店家（啟用+停用），含 Logo、名稱、管理員 Email、商品數量、狀態徽章。
2. **在** 篩選列選擇「停用」狀態，**當** 查詢，**則** 只顯示停用店家。
3. **在** 搜尋欄輸入部分店家名稱，**當** 搜尋，**則** 列表只顯示名稱包含此關鍵字的店家。

---

### 使用者故事 2 — Admin 停用店家並了解級聯影響（優先級：P1）

Admin 需要停用違規或停業的店家，確認了解並接受停用帶來的連鎖影響後才執行。

**此優先級的原因**：停用為高影響操作，必須有明確的使用者確認流程防止誤操作。

**獨立測試**：建立測試店家並上架商品，執行停用流程，確認確認 Modal 顯示所有警告，確認後級聯停用正確執行。

**驗收情境**：
1. **在** 啟用狀態的店家，**當** Admin 點擊「停用」，**則** 彈出確認 Modal，顯示完整的級聯影響清單。
2. **在** 停用確認 Modal，**當** Admin 未正確輸入店家名稱就點擊確認，**則** 確認按鈕保持 disabled。
3. **在** 正確輸入店家名稱並確認，**當** API 執行成功，**則** 店家狀態變為「停用」，商品在前台不可見，廣告停用。
4. **在** 已停用店家，**當** Admin 查看詳情，**則** 顯示「此店家已停用。重新啟用後，商品與廣告需手動重新上架」警告橫幅。

---

### 使用者故事 3 — 店家管理員編輯自家店家資訊（優先級：P1）

StoreOwner 需要更新店家 Logo、描述、聯絡方式，保持店家頁面資訊最新。

**此優先級的原因**：店家自主管理資訊是基本功能需求。

**獨立測試**：StoreOwner 登入，修改店家 Logo 和描述並儲存，確認前台店家頁面更新。

**驗收情境**：
1. **在** StoreOwner 進入「店家資訊管理」，**當** 上傳新 Logo 並修改簡短描述後儲存，**則** Toast「店家資訊已更新」，前台店家頁面反映變更。
2. **在** STORE_EDITOR 登入後，**當** 進入「店家資訊管理」，**則** 所有欄位為唯讀，顯示「您的角色無法編輯店家資訊」提示。
3. **在** 簡短描述超過 100 字，**當** 嘗試儲存，**則** 顯示驗證錯誤「簡短描述最多 100 字」。

---

### 使用者故事 4 — Admin 重新啟用停用的店家（優先級：P2）

停用店家重新開業，Admin 啟用店家，並告知店家管理員需手動重新上架商品。

**此優先級的原因**：啟用流程重要但較少見，且有明確的手動後續操作提示。

**驗收情境**：
1. **在** 店家狀態為「停用」，**當** Admin 點擊「啟用」並確認，**則** 店家狀態變為「啟用」，前台可見。
2. **在** 啟用確認 Modal，**當** 顯示提示，**則** 包含「啟用後，原有商品與廣告不會自動恢復，需店家管理員手動上架。」

---

### 邊界情況

- 停用店家後，StoreOwner 嘗試登入，後端返回 401 / 403（帳號失效），前端顯示「您的帳號已被停用，請聯繫管理員」。
- 店家 Logo 上傳超過 5MB，顯示大小限制錯誤。
- 完整描述（富文本）含不安全的 HTML 標籤（如 `<script>`），前端需過濾或依賴後端 sanitization。
- Admin 進入 StoreOwner 才能訪問的 `/admin/store/profile` 路由，導向 403 頁面（此路由為 StoreOwner 專用）。
- 店家無商品時，商品數量顯示「0」，連結仍可跳轉至商品管理（顯示空列表）。

## API 串接規格

### 店家管理

| 動作 | Method | 端點 | 主要 Request 欄位 | 主要 Response 欄位 | 前端 UI 狀態 |
|------|--------|------|------------------|--------------------|-------------|
| 取得店家列表 | GET | `/api/admin/stores` | — | `[{id, name, shortDescription, logoUrl, status, ownerEmail, productCount, createdAt}]` | loading → 表格渲染 |
| 取得店家詳情 | GET | `/api/admin/stores/{id}` | — | `{id, name, shortDescription, longDescription, logoUrl, coverImageUrl, email, phone, address, businessHours, facebookUrl, instagramUrl, status, owner:{id,email,displayName}, createdAt}` | loading → 詳情渲染 |
| 更新店家資訊 | PUT | `/api/admin/stores/{id}` | `name, shortDescription, longDescription, logoUrl, coverImageUrl, email, phone, address, businessHours, facebookUrl, instagramUrl` | `{id, name, ...}` | 按鈕 loading → Toast |
| 啟用店家 | POST | `/api/admin/stores/{id}/enable` | — | `{id, status: "ENABLED"}` | Modal loading → 狀態更新 |
| 停用店家 | POST | `/api/admin/stores/{id}/disable` | — | `{id, status: "DISABLED"}` | Modal loading → 狀態更新 |
| 取得店家選單 | GET | `/api/admin/stores/options` | — | `[{id, name}]` | 下拉選單載入 |

## 功能需求（前端 UI）

### 介面需求

- **FR-UI-001**：店家列表 Logo 欄位顯示圓形裁切縮圖（40×40px），若無 Logo 顯示店家名稱首字縮寫佔位圖。
- **FR-UI-002**：停用店家確認 Modal 必須有「輸入店家名稱確認」機制，只有輸入正確才啟用確認按鈕（防誤操作）。
- **FR-UI-003**：停用店家的確認 Modal 使用紅色 Header，強調這是不可輕易執行的操作。
- **FR-UI-004**：已停用店家在詳情頁頂部顯示全寬橘色警告橫幅「此店家已停用」。
- **FR-UI-005**：店家詳情頁的社群連結（Facebook、Instagram）以 icon + 連結樣式顯示，點擊在新分頁開啟。
- **FR-UI-006**：ROLE_STORE_OWNER 的「店家資訊管理」頁面不顯示「店家管理員」資訊欄（避免顯示自己的帳號資訊），此欄位為 Admin 專屬。
- **FR-UI-007**：編輯頁面「簡短描述」欄位下方顯示即時字數計數（X / 100 字）。
- **FR-UI-008**：商品數量欄位為可點擊數字，點擊後導向該店家的商品管理列表（帶店家 ID 篩選）。
- **FR-UI-009**：啟用店家的確認 Modal 顯示「注意：啟用後商品與廣告不自動恢復，需手動重新上架」提示。

### 狀態管理

- **SM-001**：店家列表初始載入使用 skeleton loading。
- **SM-002**：停用 / 啟用成功後，即時更新列表和詳情頁的狀態徽章（樂觀更新）。
- **SM-003**：店家資訊儲存成功後，Toast「店家資訊已更新」，留在編輯頁面或返回詳情頁（依 UX 設計決定）。
- **SM-004**：離開編輯頁前若有未儲存變更，顯示「有未儲存的變更，確定離開？」確認對話框。
- **SM-005**：篩選條件變更自動觸發列表查詢（關鍵字 debounce 300ms）。
- **SM-006**：停用確認 Modal 的「店家名稱輸入」欄位監聽 input 事件，即時比對輸入值與店家名稱是否完全一致（大小寫敏感）。

## API 驗證清單

- **AV-001** ✅：`GET /api/admin/stores` Response 包含 `ownerEmail` 和 `productCount` — 列表頁顯示管理員 Email 和商品數量有直接資料來源。
- **AV-002** ✅：`GET /api/admin/stores/{id}` 包含完整店家資訊（`owner`, `businessHours`, `facebookUrl`, `instagramUrl`）— 詳情頁渲染完整。
- **AV-003** ⚠️：停用店家後帳號是否同步停用 — 後端 FR-004 說明「停用店家 → 所有商品下架、廣告停用、店家隱藏」，但未明確說明關聯 StoreOwner / StoreEditor 帳號是否同時停用；前端警告文字需與後端行為一致。
- **AV-004** ⚠️：`businessHours` 欄位格式 — 後端 spec 包含 `businessHours` 欄位但未說明格式（JSON 物件、字串還是結構化格式？）；前端編輯 UI 設計需等待後端確認格式（可能為自由文字或週期性時間設定）。
- **AV-005** ❌：`GET /api/admin/stores` 無篩選/分頁參數 — 若店家數量增多，全量載入後前端篩選效能不足；需確認後端是否支援 query param 篩選（`?status=&keyword=`）。
- **AV-006** ✅：`PUT /api/admin/stores/{id}` 同時支援 Admin 和 StoreOwner 更新 — 後端依角色控制存取，前端無需特殊處理。
- **AV-007** ⚠️：ROLE_STORE_OWNER 的 API 路由 — StoreOwner 編輯自家店家應呼叫 `PUT /api/admin/stores/{id}`（帶自家店家 ID），需確認後端是否有根據 JWT 自動套用店家 ID 的機制，或前端需從 UserPrincipal 取得 storeId。
- **AV-008** ❌：重新啟用後商品不自動恢復的通知機制 — 啟用店家後，前台的警告提示（商品需手動重新上架）需要前端 UI 確認，但後端並未有 API 支援「顯示待重新上架商品數量」；前端只能靜態顯示提示文字。

凡例：✅ 已確認一致 | ⚠️ 需要確認 | ❌ 發現缺口或不一致

## 成功標準

### 可量化的成果

- **SC-001**：Admin 可在 30 秒內找到特定店家（透過搜尋關鍵字），並進入其詳情頁。
- **SC-002**：店家列表在 50 筆以內，載入時間不超過 2 秒。
- **SC-003**：停用店家後，前台玩家在 5 秒內無法看到此店家及其商品（CDN 快取 + 後端立即生效）。
- **SC-004**：StoreOwner 更新店家資訊後，前台店家頁面在 30 秒內反映最新資訊。
- **SC-005**：停用確認 Modal 的名稱輸入驗證確保 0 誤操作風險（必須精確輸入店家名稱）。
- **SC-006**：ROLE_STORE_EDITOR 進入店家資訊管理頁面時，100% 顯示唯讀模式（無法提交表單）。
